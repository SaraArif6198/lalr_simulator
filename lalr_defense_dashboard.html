What is an LR(1) Item?
The atomic unit of the LALR(1) automaton

An LR(1) item is a grammar production with a dot (•) showing how far parsing has progressed, plus a lookahead token showing what must follow. Three numbers uniquely identify it: prodIdx, dot, lookahead. Our code stores it as a string: "prodIdx_dot_lookahead".

📐 LR(1) Item Anatomy
// Item: "E → E • + T" with lookahead "$"
prodIdx = 2 ← which production
dot = 1 ← how many symbols consumed
lookahead= "$" ← what must follow LHS
→ stored as: "2_1_$"
🔄 Shift vs Reduce Decision
If dot is BEFORE a symbol → can SHIFT (read next token)
✅ E → E • + T, $ → dot before '+', so SHIFT on '+'
If dot is AT THE END → must REDUCE (fold into non-terminal)
✅ E → E + T •, $ → dot at end, so REDUCE using this rule

runLexer() — Code Sanitization
First thing: strip comments, prepare input

The lexer is the security guard at the factory gate. Before any real work, it strips all // line comments and /* block comments */ using a regular expression. The input code then becomes a clean character stream ready for tokenization.

🧹 Comment Stripping in Action
Raw Input
// declare x
int x;
/* assign */
x = 5 + 3;
After Sanitize
 
int x;
 
x = 5 + 3;
📌 Regex: /\/\*[\s\S]*?\*\/|\/\/.*/g
✅ /\*...*\/ → block comments removed (non-greedy .*?)
✅ //.* → line comments removed (to end of line)

Now the lexer checks what the grammar needs. It calls terminals.includes('id') and terminals.includes('num'). Why? Because if the grammar never mentions 'num', there's no point classifying numbers. This is vocabulary-aware scanning — the lexer adapts to the grammar.

🔑 Token Priority — Longest Match First

Operators are sorted by length descending. This prevents == from being tokenized as two separate = signs. Longest terminal always wins the match.

Token Stream Generation
Character-by-character scanning loop

The main while(cursor < sanitized.length) loop reads the remaining string from cursor position, tries every pattern in order, and the first match wins. Cursor advances by the match length. This is the classic maximal munch scanning algorithm.

parseGrammar() — Production Splitting
Converting raw text grammar into structured data

The grammar arrives as plain text like "E -> E + T | T". The parser splits each line on "->" or "::=", extracts the left-hand side, then splits alternatives on "|". Each alternative is further split by whitespace into individual symbols.

🔪 Splitting Process

→
lhs: "E"
rhs: "E + T | T"
↓ split '|' → two alternatives
prod 0: E → [E, +, T]
prod 1: E → [T]

Grammar augmentation is critical for LR parsing. We add a new start symbol E' → E (with a prime). This creates a single unambiguous acceptance state. When the parser sees E' → E • with lookahead $, it knows parsing is complete — accept!

⭐ Why Augmentation?
Without E': Multiple start states could exist → ambiguous acceptance
✅ With E' → E: Only ONE accept state possible → clean termination
✅ E' gets prodIdx=0 → its reduce action → "acc" (not Rk)

Fixed-Point Iteration — The Detectives
computeNullableFirstFollow() — runs until no more changes

The algorithm runs a while(changed) loop — it keeps iterating until no new information is discovered. This is called a fixed-point algorithm. Three detective sets are computed: Nullable (can it vanish?), FIRST (what appears first?), FOLLOW (what comes after?).

🔍 FIRST Set — Example Grammar: E→E+T|T; T→num|id
SymbolFIRST SetWhy?
num{num}terminal is its own FIRST
id{id}terminal is its own FIRST
T{num, id}T→num and T→id, so both
E{num, id}E→T (so FIRST(T)), E→E+T (so FIRST(E) itself)
E'{num, id}E'→E so FIRST(E)
📡 FOLLOW Set Propagation Rules
Rule 1: FOLLOW(start) always contains $ (EOF marker)
✅ For E→E+T: FOLLOW(E in position 0) gets FIRST(+T) = {+}
✅ For E→E+T: + not nullable, so stop. FOLLOW(T) gets FOLLOW(E) = {$, +} wait...
Rule 2: If β after B is nullable → FOLLOW(B) gets FOLLOW(LHS)

computeClosureLR1() — The Closure Machine
Expanding items recursively with lookahead propagation

Closure is how we expand a set of LR(1) items. When the dot is before a non-terminal B, we add all productions of B with dot at position 0. The new lookaheads are computed as FIRST(βa) — where β is the rest of the right side and a is the original lookahead.

🔄 Closure Expansion — State I₀
INITIAL ITEM
E' → • E , $
↓ dot before E (non-terminal) → expand E's productions with lookahead FIRST(a) = FIRST($) = {$}
AFTER CLOSURE
E' → • E , $
E → • E + T , $
E → • E + T , +
E → • T , $
E → • T , +
T → • num , $
T → • num , +
T → • id , $
T → • id , +

The code uses a queue (array + head pointer) — not recursion — to avoid stack overflow. It's a BFS expansion: take item from queue, expand it, add new items back, repeat until queue is exhausted. This is the textbook LR(1) closure algorithm!

computeGotoLR1() — The Shift Operation
Moving the dot one step forward on symbol X

GOTO(I, X) finds all items in state I where the dot is before X, advances the dot by one, collects these "shifted" items, and calls closure on them. The result is the new destination state — the edge in our DFA.

Shift & Goto Table Population
lalrTransitions.forEach → ACTION and GOTO entries

The code loops over every lalrTransition (from, symbol, to). If symbol is a terminal → it's a Shift → adds "S{to}" to actionTable[from][symbol]. If symbol is a non-terminal → it's a Goto → adds number to gotoTable[from][symbol].

S# = Shift to state # R# = Reduce using prod # acc = Accept! ✓ Number = Goto next state

Reduce entries come from items where the dot is at the end of a production. The code loops over every item in every LALR state. When dot == prod.rhs.length → reduce on this item's lookahead. Special case: if prodIdx == 0 (the augmented rule E'→E) and lookahead == '$' → Accept!

⚡ Reduce Entry Logic — Step by Step
For item "T → num •, $" : dot(1) == rhs.length(1) → dot at end → REDUCE
✅ prodIdx ≠ 0 (not augmented rule) → add R{prod.originalIdx} = R3
For item "E' → E •, $" : dot at end AND prodIdx==0 AND lookahead=='$'
✅ → addAction(state, '$', 'acc') → ACCEPT!
📊 Epsilon Production Special Case

If a production is A → ε, the dot is conceptually "at the end" even at position 0. Code checks: isEpsilonProd = (rhs.length===1 && rhs[0]===EPSILON). In this case, popCount = 0 — nothing is popped from the stack.

The Ambiguity Police — addAction()
Detecting Shift-Reduce and Reduce-Reduce conflicts

The addAction() helper checks before writing to the table. If a cell already has an entry and the new entry differs → CONFLICT detected! It categorizes it as Shift-Reduce (S vs R) or Reduce-Reduce (R vs R) and logs it to the conflicts array.

🚨 Conflict Classification Logic
const conflictType =
  (existing.startsWith('S') && actionStr.startsWith('R')) ||
  (existing.startsWith('R') && actionStr.startsWith('S'))
  ? 'Shift-Reduce' : 'Reduce-Reduce';
⚠️ Example: Dangling-else style Shift-Reduce Conflict
State 5, symbol '+': existing="S5" vs new="R1"
→ Shift-Reduce conflict! Both actions in same cell.
→ Stored as "S5/R1" in table, logged to conflicts[]

runParseSimulator() — LALR Trace
Executing the parser using ACTION/GOTO tables

The simulator runs a loop: look at stack top state and current token, consult actionTable. If Shift → push new state and token. If Reduce → pop symbols, create parent AST node, consult gotoTable for next state. If acc → success!

generateTAC() — Three-Address Code
Post-order traversal emitting intermediate representation

The TAC generator does post-order traversal — evaluate children first, then produce the parent instruction. Each binary operation becomes t_n = arg1 op arg2. Temporary variables (t1, t2, t3...) are auto-generated by newTemp(). This is the standard compiler intermediate representation!

⚡ TAC Generation — "x = 5 + 3 * 2"
Post-order evaluation (deepest subtrees first):
t1 = 3 * 2← deepest operation first
t2 = 5 + t1← use t1 as operand
x = t2← final assignment
Parentheses → emit(inner child) — brackets stripped automatically
✅ Operator found in children → emit TAC instruction, return temp name
✅ Assignment found → emit "dest = src", return dest name
Fallback: if 1 meaningful child → pass its value up the tree
